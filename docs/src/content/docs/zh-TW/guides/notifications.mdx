通知目的地會把警示與事件變更傳送到外部系統。目的地屬於專案，並可由多個警示規則重複使用。

## 目的地類型

| 類型     | 常見用途                                       |
| -------- | ---------------------------------------------- |
| Webhook  | 把結構化事件傳送到自動化或事件處理平台         |
| Slack    | 透過 Incoming Webhook 把事件貼到 Slack Channel |
| Discord  | 透過 Webhook 把事件貼到 Discord Channel        |
| Telegram | 透過 Telegram Bot 傳送訊息                     |
| 電子郵件 | 透過站台 SMTP 設定傳送郵件                     |

## 建立目的地

1. 開啟**警示**，再進入**通知**。
2. 選擇**新增通知**。

<ProductScreenshot src={notificationTypePickerScreenshot} alt="包含 Webhook、Slack、Discord、Telegram 與電子郵件類型的通知編輯器" caption="先選擇傳送管道，Netstamp 接著只顯示該供應商需要的設定。" />

3. 選擇類型並輸入所需 Endpoint、Token、Chat 或收件人資料。
4. 儲存目的地。
5. 傳送測試通知。

附加到正式環境規則前先測試。儲存成功只代表欄位被接受；成功的測試才能驗證網路存取與外部憑證。

## 附加到規則

編輯警示規則並選擇一個或多個通知目的地。同一目的地可附加到多個規則，請使用能同時辨識服務與受眾的名稱，例如 `slack-platform-oncall`。

請一起考量規則嚴重程度與通知受眾。不是每個 Warning 都需要通知接收 Critical 事件的相同頻道。

## Email 需求

Email 目的地需要可用的全站 SMTP 設定。測試失敗時，系統管理員應先確認 SMTP Host、Port、憑證、寄件人、加密模式與控制器日誌。

SMTP 設定請參閱[驗證與電子郵件](/zh-TW/docs/installation/authentication-and-email/)。

## 處理密鑰

Webhook URL、Bot Token 與 SMTP 憑證都是密鑰。限制可編輯目的地的人員、避免在截圖或支援資料中顯示數值，並在權限變更或可能外洩時輪替。

儲存後應用程式可能遮蔽密鑰。遮蔽值代表密鑰仍被保存，不是可提供給其他管理員的可還原副本。

## 排查傳送問題

若測試或事件通知未送達：

- 確認目的地已啟用且測試成功。
- 確認警示規則已選取該目的地。
- 檢查傳送時間附近的控制器日誌。
- 驗證控制器的對外 DNS 與 HTTPS 或 SMTP 存取。
- 檢查外部 Rate Limit、Channel 權限、收件人過濾與垃圾郵件處理。
- 若供應商回報憑證無效，請輪替或重新輸入。

事件解決時可能會另行傳送恢復通知。下游自動化應同時測試觸發與恢復兩種處理。
