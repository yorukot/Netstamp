Traceroute 會顯示探測器與目標之間觀察到的網路躍點。它最適合當作佐證：用來解釋已在 Ping、TCP 或 HTTP 中發現的特定路徑變化，不要單獨當成可用性測試。

使用本指南以前，請先閱讀[分析範圍與時間控制項](../)。

## 選擇調查範圍

需要躍點表格或單次執行時，請使用精確的一筆探測器與檢查指派；需要彙總路徑圖時，則使用較廣的範圍：

| 範圍                             | 分析顯示內容                                               |
| -------------------------------- | ---------------------------------------------------------- |
| 一個探測器與一個 Traceroute 檢查 | 彙總拓樸、所選單次執行的躍點診斷與時間線                   |
| 一個探測器與多個檢查             | 該探測器觀察到的拓樸；非 Traceroute 檢查使用自己的序列面板 |
| 多個探測器與一個 Traceroute 檢查 | 所選探測器對該目標的彙總拓樸                               |
| 多個探測器與多個檢查             | 除非其中一側縮小成一個探測器或一個檢查，否則不顯示合併拓樸 |

時間範圍要短到足以區分路徑變更。過大的範圍可能把數條有效路徑合併成一張複雜拓樸圖。

路徑圖會辨識：

- 起點 **Agent** 或探測器。
- 保留執行中觀察到的中間節點。
- 有回應時的目的地。
- 依可用觀察結果計算的正常、高 RTT 與遺失狀態。
- 不同執行走過不同路徑時的替代 Edge。

使用路徑圖找出路徑從哪裡分歧，或受影響探測器從哪裡開始與健康探測器走不同路線。接著選取一筆精確指派，並使用時間線檢查實際執行。

:::note Hostname 是為觀察到的位址解析出的標籤。名稱變更不一定代表底層位址或路徑發生變化。 :::

## 從時間線選取執行

<ProductScreenshot
	src={tracerouteRunTimelineScreenshot}
	alt="包含延遲資料點、遺失、路徑變更狀態與所選執行的 Traceroute 時間線"
	caption="選取原始資料點可載入該次執行的躍點；拖曳一段時間則會縮小整個分析區間。"
/>

時間線會繪製所選時間區間內最後一個有回應躍點的 RTT。圖例會區分正常執行、高 RTT、遺失、路徑變更與目前選取的執行。

時間線行為會依回傳解析度而不同：

- **原始資料點**代表一次保留執行。選取後會把該次執行載入躍點表格，並將開始時間保存在網址。
- **彙總資料點**代表包含多次執行的 Bucket。選取後會把分析範圍縮小到該 Bucket，以便要求原始證據。
- 在時間線上拖曳會把全域分析區間改為絕對範圍。

路徑變更標記表示觀察到的路徑與前一條不同，不能證明發生中斷。請載入變更前後的執行，再比較相同區間內的服務行為。

## 閱讀單次執行的躍點表格

	src={tracerouteHopTableScreenshot}

	caption="躍點表格描述目前選取的一次執行；下游回覆會決定中間遺失訊號是否持續向後傳播。"

每列代表所選執行中的一個 Hop index：

| 欄位      | 意義                                   |
| --------- | -------------------------------------- |
| 節點      | 可用時顯示解析後的 Hostname 與觀察位址 |
| 遺失      | 在該躍點未收到回覆的傳送訊息比例       |
| 延遲      | 以共同刻度顯示最小、平均與最大 RTT     |
| Median    | RTT 樣本中間值，較不受單一極端回覆影響 |
| 範圍      | 該躍點的最小與最大 RTT                 |
| Sent/Recv | 傳送的探測訊息與收到的回覆數量         |
| 狀態      | Netstamp 對該列的診斷分類              |

將躍點延遲與上一個有回應躍點比較。單一路由器的高數值不等於服務延遲；請確認增加是否持續出現在下游與目的地。

## 了解躍點狀態

| 狀態         | Netstamp 分類方式                                    | 判讀                                             |
| ------------ | ---------------------------------------------------- | ------------------------------------------------ |
| 正常         | 沒有被標記的遺失或顯著 RTT 增加                      | 此次執行沒有偵測到問題                           |
| 無回覆       | 已傳送訊息，但該躍點沒有回覆                         | 路由器可能忽略或限制 Traceroute 流量             |
| RTT 跳升     | 平均 RTT 比上一個有回應躍點增加超過 10 ms 且超過 20% | 可能有路徑或處理變化；確認是否持續到下游         |
| 僅路由器遺失 | 此躍點有遺失，但後續有回應躍點沒有持續遺失           | 通常是路由器 ICMP Rate limit，而不是轉送流量遺失 |
| 持續向後遺失 | 每一個有回應的下游躍點也有遺失                       | 較強的證據顯示遺失從此處或更前方開始             |
| 最終躍點遺失 | 最後一個有回應躍點存在遺失                           | 目的地或最後一段可見路徑可能受到影響             |

這些狀態是診斷，不是根本原因結論。防火牆、Control-plane 保護、負載平衡與不完整回覆都可能改變 Traceroute 能看見的資訊。

## 避免常見誤判

### 中間躍點沒有回覆

若後續躍點與目的地仍有回覆，代表沒有回覆的路由器仍在轉送流量。請把缺少的列視為可見性不足，不是服務遺失的證明。

### 一個躍點回報遺失，但後續躍點正常

路由器可能限制送往自身的回覆，但仍正常轉送 Transit 流量。Netstamp 會標記為**僅路由器遺失**。如果沒有下游遺失或服務影響，不要因此升級事件。

### RTT 在一個躍點上升，後續又下降

路由器可能降低自身回覆的優先級。路徑延遲不可能在後面被消除，所以未持續到下游的尖峰不能證明 Transit 流量承受相同延遲。

### 路徑改變但服務保持健康

路由協定、Anycast、ECMP 與 Load Balancer 都可能選擇另一條有效路徑。只有當路徑變更與持續遺失、延遲、連線失敗或 HTTP 劣化同時發生時才需要調查。

### 不同探測器顯示不同路徑

探測器使用不同 Provider、區域、DNS 答案或 Peering 關係時，這是預期行為。請利用差異解釋影響範圍，而不是期待拓樸完全相同。

## 考慮 Traceroute 限制

Traceroute 無法在所有網路中顯示完整的正向與反向資料路徑。判讀時請考慮：

- 回程流量可能走不同於正向探測訊息的路徑。
- MPLS、Tunnel、NAT、防火牆與私有網路可能隱藏躍點。
- ECMP 與 Per-packet Load Balancing 可能產生數條有效路徑。
- ICMP 與 UDP Traceroute 流量可能受到不同於 TCP 或 HTTP 的過濾或降權。
- 解析出的躍點名稱可能缺少、過期、過於通用或造成營運誤導。
- 最後一個有回應躍點不一定是應用程式主機。

Traceroute 檢查目前不支援警示規則。請使用 Ping、TCP 或 HTTP 服務證據建立警示，再於調查期間使用 Traceroute。

## 調查流程

1. 在 Ping、TCP 或 HTTP 中找出事件區間。
2. 為一個受影響探測器開啟相符的 Traceroute 檢查。
3. 設定相同的絕對時間區間。
4. 檢查彙總路徑圖是否出現路徑分歧。
5. 使用時間線選取事件發生前、期間與之後的執行。
6. 比較躍點表格中第一個持續存在的 RTT 或遺失變化。
7. 使用未受影響的探測器重複比較。
8. 分享包含所選執行的網址，並註明時區。

返回 [Ping、TCP 與 HTTP 分析](../analyze-measurements/)，確認路徑證據是否符合使用者可觀察到的服務行為。
